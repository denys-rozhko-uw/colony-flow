# Постоянные инструкции для Codex

Этот файл действует для всего репозитория `C:\Projects\game`. Он предназначен в том числе для модели sol, которая будет реализовывать игру по плану. Инструкции пользователя и системные ограничения имеют приоритет. Работа с этим репозиторием не требует специальной модели, внешних плагинов или параллельных агентов.

## 1. Цель и порядок чтения

Разработать Ant Picture — одиночную головоломку по игровому принципу Colony Flow на Godot 4.5.1. Первая законченная версия — Windows, 20 собственных уровней. Android — отдельное продолжение.

Перед изменениями:

1. Прочитать этот файл.
2. Прочитать [ARCHITECTURE.md](ARCHITECTURE.md): правила, решения A01–A06, API, схемы и инварианты.
3. Проверить этап в [ROADMAP.md](ROADMAP.md) и статусы/зависимости в [TASKS.md](TASKS.md).
4. Осмотреть фактические файлы и изменения пользователя. Документы описывают целевое состояние, а не доказывают наличие реализации.
5. Выбрать первую доступную задачу в рамках запроса пользователя и отметить её `[-]` перед реализацией.

При различии документов: ARCHITECTURE.md определяет игровые правила и контракты, ROADMAP.md — границы этапов, TASKS.md — порядок и проверку задач. Сначала устранить противоречие в документах, а не выбирать удобную трактовку в коде. Явное новое указание пользователя важнее старого плана.

Если пользователь просит только план или анализ, не создавать игру автоматически. Если просит реализацию, продолжать в пределах порученного объёма, последовательно закрывая зависимости. Завершение одной задачи само по себе не повод прекращать всю порученную работу.

## 2. Среда и ограничения

- Движок: Godot **4.5.1 stable**, GDScript 4, Compatibility.
- Локальный console executable: `C:\Godot\Godot_v4.5.1-stable_win64_console.exe`.
- GUI executable: `C:\Godot\Godot_v4.5.1-stable_win64.exe`.
- Корень проекта: `C:\Projects\game`, `project.godot` создаётся именно здесь.
- Не изменять установку Godot, другие проекты в C:\Godot и системные настройки ради обычной разработки.
- Не обновлять движок, не переходить на C#/3D и не добавлять зависимости без причины, записи ADR и проверки совместимости.
- Не добавлять backend, HTTP-запросы, телеметрию, рекламу, платежи и аккаунты в 1.0.
- Не скачивать и не использовать ресурсы оригинальной игры автоматически; создавать собственные или использовать ресурсы с известным разрешением и указанием происхождения.
- Не хранить ключи подписи, пароли, персональные данные и содержимое пользовательских сохранений в репозитории.
- Не поручать работу другим агентам, если пользователь отдельно этого не просил.

При отсутствии движка, шаблонов экспорта или прав описать конкретный блокер и продолжить независимую часть задачи. Не выдавать симуляцию запуска, прочитанный код или успешный импорт за реальное прохождение игры.

## 3. Стиль кода

- Кодовые имена и комментарии API — понятные английские; общение, документация и первый UI — на русском. Комментарии могут быть на русском, если это делает объяснение причины понятнее.
- Файлы/функции/переменные: `snake_case`; `class_name`: `PascalCase`; константы и значения enum: `UPPER_SNAKE_CASE`.
- Явно типизировать аргументы, возвращаемые значения и поля доменной модели. Variant допустим при чтении JSON до проверки, а не как основной интерфейс игры.
- Табуляция для отступов GDScript. Порядок в скрипте: class_name/extends, сигналы, enum/константы, экспортируемые поля, обычные поля, методы жизненного цикла, публичные методы, приватные методы.
- Один компонент — одна понятная ответственность. Не создавать универсальный фреймворк ради одной игры.
- Предпочитать короткие методы с явными проверками входных данных. Комментировать причину и инвариант, а не пересказывать очевидный код.
- Повторяющиеся игровые параметры хранить в одном месте; не дублировать число слотов, лимиты рейсов и частоту тиков по сценам.
- В домене — RefCounted и данные. В представлении — Nodes, сцены, Tween и сигналы. Не получать узлы через абсолютные пути из доменной модели.
- Избегать изменяемого глобального состояния, God object, глобального event bus и ненужных Autoload. Сервисы передавать явно через AppRoot/GameSession.
- Не модифицировать внутренние массивы модели через снимки. Не переиспользовать изменяемое состояние Resource между уровнями.
- Обрабатывать результаты FileAccess/JSON/DirAccess. Ошибки контента возвращать с путём поля; не подставлять случайные значения ради продолжения игры.
- Не прятать ошибки предупреждениями ignore без объяснения. Исправить новые ошибки/предупреждения, внесённые своим изменением.

## 4. Правила, которые нельзя случайно нарушить

1. Только Simulation изменяет блоки, резервы, квоты, рейсы и слоты.
2. Callback анимации, звук и количество визуальных муравьёв не определяют результат партии.
3. Симуляция использует целые тики 10 Гц и фиксированный порядок обработки. Никакой случайности, часов ОС или зависимости от FPS в доменных правилах.
4. Удаление блока происходит при заборе; уменьшение remaining — при доставке. Резервирование не равно доставке.
5. Пять занятых слотов не означают немедленный проигрыш. Применять условие LOST из архитектуры после полного тика.
6. При рестарте очищать команды и время, менять session_id, отменять старые визуальные события.
7. Пауза останавливает и модель, и движение. Возврат с паузы не компенсирует пропущенное время.
8. Доступность коробки задаёт граф blocked_by, доступность блока — ReachabilityPolicy. UI их только показывает.
9. Структурная валидность уровня и равенство квот не доказывают его проходимость. Нужен успешный solution_order через ту же Simulation.
10. Новые уровни 1.0 должны решаться без быстрых кликов, таймеров и платных спасений.

## 5. Правила изменения архитектуры

Обычное исправление внутри согласованных контрактов не требует отдельного согласования. При изменении архитектуры в рамках порученной задачи:

1. Объяснить проблему и минимальное решение.
2. Обновить актуальный текст ARCHITECTURE.md и добавить запись ADR в его конец.
3. Обновить API, схемы, fixtures, задачи и зависимости, которых касается изменение.
4. Если меняются игровые правила — обновить ruleset_id и заново проверить все решения уровней. Не менять смысл frontier_v1 молча.
5. Если меняется формат сохранений/уровней — определить версию и миграцию либо явно отказать в неподдерживаемой версии без потери файла.
6. Только после этого считать новый код соответствующим плану.

Не переписывать архитектуру целиком ради локальной ошибки. Не менять критерии готовности задним числом, чтобы скрыть провал теста. Смена платформы 1.0, удаление требуемой функции или добавление монетизации выходит за текущий план: сначала описать влияние и уточнить намерение пользователя, продолжая независимую работу.

## 6. Рабочий цикл и Git

- Проверить состояние рабочей папки перед изменениями. Не отменять, не затирать и не форматировать посторонние изменения пользователя.
- Предпочитать небольшие завершённые изменения по задачам. Не создавать пустые сцены/скрипты для всех будущих компонентов заранее.
- Для поиска использовать `rg` / `rg --files`, если доступны.
- Не использовать `git reset --hard`, очистку рабочего дерева и удаление данных без явного запроса.
- Не коммитить и не публиковать изменения автоматически, если пользователь этого не поручал. Новые ветки при необходимости начинать с `codex/`.
- Если Git сообщает dubious ownership, не менять глобальный safe.directory. Для проверки конкретного этого репозитория допустима разовая команда `git -c safe.directory=C:/Projects/game status --short`.
- Не редактировать `.git` вручную. Исходники и настройки проекта — в рабочем дереве; кеш `.godot/` и сборки не включать в коммиты.
- Не переносить файлы из C:\Godot\2dTopDown без отдельной причины и проверки содержимого.
- После реализации проверять diff, запускать подходящие проверки и обновлять TASKS.md по фактическому результату.

## 7. Проверки и команды

Команды ниже — целевые команды после создания соответствующих файлов. На момент написания плана `project.godot`, runner и инструменты ещё отсутствуют. Не пытаться запускать несуществующий тест и не считать его пропуск успехом.

PowerShell, рабочая папка `C:\Projects\game`:

```powershell
$godotBin = 'C:\Godot\Godot_v4.5.1-stable_win64_console.exe'
& $godotBin --version
```

После T02 — импорт и проверка ресурсов:

```powershell
& $godotBin --headless --path 'C:\Projects\game' --import
```

После T04 — все доступные тесты либо один затронутый suite:

```powershell
& $godotBin --headless --path 'C:\Projects\game' --script res://tests/run_tests.gd
& $godotBin --headless --path 'C:\Projects\game' --script res://tests/run_tests.gd -- --suite=domain
```

После T13 — весь контент и решения:

```powershell
& $godotBin --headless --path 'C:\Projects\game' --script res://tools/validate_levels.gd
& $godotBin --headless --path 'C:\Projects\game' --script res://tools/verify_solutions.gd
```

После T14 — короткий запуск основной сцены без окна (только проверка старта, не визуальная приёмка):

```powershell
& $godotBin --headless --path 'C:\Projects\game' --quit-after 120
```

GUI запускать через редактор либо штатно открывать основную сцену; для фоновых вспомогательных процессов на Windows использовать скрытое окно. Создание видимого окна игры оправдано ручной проверкой UI. При автоматизации не считать истечение времени доказательством прохождения.

После T30 и создания каталога сборки, preset и установки export templates:

```powershell
& $godotBin --headless --path 'C:\Projects\game' --export-release 'Windows Desktop' 'C:\Projects\game\builds\windows\AntPicture.exe'
```

Каждую команду проверять по `$LASTEXITCODE` и диагностике. Не запускать следующий зависимый шаг после провала предыдущего. `--quit-after` считает кадры/итерации, а не секунды. Успешный exit code не заменяет проверку лога на ошибки скриптов и ресурсов. Runner и инструменты обязаны корректно возвращать 1 при обнаруженных ошибках.

### Какие проверки обязательны

| Изменение | Минимальная проверка |
|---|---|
| Только документация | Ссылки, ID задач, зависимости, непротиворечивость правил; запуск игры не нужен |
| Доменная логика | Import + domain suite + regression для исправленного дефекта + все witnesses, если изменились правила |
| JSON/загрузчик/validator | Content suite + validate_levels + verify_solutions |
| GameSession/ввод/пауза | Integration suite + GUI-сценарий затронутого поведения |
| UI/графика/звук | Import + ручной просмотр/прослушивание в затронутых размерах; не писать бессмысленные тесты цвета кнопки |
| SaveService/схема save | Save suite, temp-каталог, восстановление/отказ записи; пользовательские saves не трогать |
| Экспорт/релиз | Полные доступные проверки, запуск экспортированной игры, чтение контента и сохранение прогресса |

Тестировать поведение и риски, а не копировать алгоритм реализации внутрь assertions. Не создавать тесты ради каждой мелкой обратимой правки. После успешных релевантных проверок не повторять весь набор без новых изменений или причин.

## 8. Общий критерий готовности задачи

- Реализовано указанное поведение, зависимости закрыты, нет скрытых заглушек на затронутом пути.
- Выполнены критерии конкретной задачи и подходящие проверки из таблицы выше.
- Новых ошибок импорта, скриптов и ресурсов нет; исправленный баг имеет проверку, если он затрагивал логику/данные.
- Сцены остаются пригодными для открытия в редакторе; отсутствие GUI-проверки указано явно.
- Документы отражают реальные API и форматы; TASKS.md содержит статус и фактическое подтверждение.
- Остаточные ограничения описаны. Задача не закрывается, если её обязательная проверка недоступна.

## 9. Как сообщать о результате и продолжать работу

Кратко сообщать: что изменилось для игрока, какие задачи закрыты, чем проверено, что осталось или заблокировано. Не перечислять все команды, если пользователь не просит технические детали. Не называть готовой всю игру после завершения каркаса или прототипа.

При продолжении после перерыва прочитать журнал TASKS.md и фактическое состояние репозитория. Не начинать заново закрытые задачи и не доверять одному checkbox при очевидном расхождении с файлами. Проверить это расхождение и исправить запись.

Если обнаружена неопределённость, которую можно локализовать безопасным решением в рамках A01–A06, зафиксировать допущение и продолжать. Не превращать обычные решения реализации в постоянные запросы разрешений. Не объявлять скрытые правила оригинала известными без наблюдений.
