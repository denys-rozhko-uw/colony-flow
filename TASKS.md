## Как работать с задачами

Обозначения: `[ ]` — не начата, `[-]` — выполняется, `[x]` — выполнена, `[!]` — заблокирована с указанной причиной. Зависимости означают завершённые задачи, не просто созданные файлы. Каждая задача закрывается только после своих критериев и общих критериев из AGENTS.md.

Для закрытой задачи добавить строку `Проверка: <команда/сценарий>; <фактический результат>; <путь к отчёту при наличии>`. Для блокировки — что именно отсутствует и что уже сделано. Не ставить `[x]` по одному факту написания кода.

Зависимости: T03.

- Runner наследуется от SceneTree, обнаруживает/регистрирует suites явно, печатает названия проваленных тестов, число проверок и завершает процесс кодом 0/1.

- Файлы тестов писать в выделенный временный каталог, не в сохранения игрока. Сбой assertion не должен оставлять процесс работающим бесконечно.

Готово: положительный контроль завершается с 0, намеренно ошибочная проверка — с 1; затем ошибочный контроль убран из обычного набора. T03 вызывает runner и учитывает результат.

Проверка: обычный runner — 112 проверок, 0 отказов; `--self-test-failure` — код 1. Фильтр suite работает, неизвестный suite возвращает код 1.

## M2. Симуляция

### [x] T08 — Реализовать доступность и пути

Зависимости: T07.
Результат: ReachabilityPolicy, domain suite для поля.

- BFS от нижней полосы, только ортогональные пустые клетки, фиксированный порядок обхода и выбора целей.
- Резерв остаётся препятствием до забора; удалённая клетка открывает путь. Кэш сбрасывается только по изменению поля, если кэш вообще нужен.

Готово: проверены нижний край, закрытая полость, узкий проход, диагональное касание, отсутствие обхода через бок/верх, выбор между равными целями. Путь не пересекает занятые клетки.

Проверка: domain suite проверяет нижний фронт, открытие верхней клетки, диагональный разрыв и резерв как препятствие; порядок целей детерминирован. Все свидетели уровней проходят тем же алгоритмом.

### [x] T09 — Реализовать запас, команды и слоты

Зависимости: T08.
Результат: очередь команд Simulation, размещение коробок и события команд.

- Последовательное применение команд на границе тика, первый свободный слот, открытие по activated_ids.
- Отклонять заблокированный ID, повтор, неизвестный ID и шестую коробку.

Готово: две команды одной коробки дают одну активацию; шесть команд за тик занимают максимум пять слотов; зависимость открывается на отправке предшественника, а не на завершении его квоты. Отказ не меняет слоты и квоты.

Проверка: domain suite покрывает заблокированную, повторную и шестую команды, первое свободное место и открытие зависимой коробки при отправке.

### [x] T10 — Реализовать резервирование и рейсы

Зависимости: T09.
Результат: целочисленные тики, назначение целей, OUTBOUND/RETURNING, доставка.

- Следовать фазам тика и лимитам 4/20 из архитектуры. Каждому рейсу соответствует отдельная цель и единица квоты.
- Удалять клетку на заборе; уменьшать remaining только при доставке; освобождать слот после последней доставки.

Готово: две коробки одного цвета не резервируют один блок; quota=1 не создаёт лишний рейс; после удаления открывается следующая цель; освобождение слота не происходит при последнем резервировании или заборе. Нет отрицательных счётчиков.

Проверка: split-color fixture, поэтапная доставка, инварианты каждого тика и успешные решения 20 уровней. Две коробки одного цвета получают разные клетки.
